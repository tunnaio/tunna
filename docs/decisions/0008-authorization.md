# ADR-0008: Authorization and key management

**Status:** Accepted
**Date:** 2026-09-14
**Deciders:** maintainer

## Context

ADR-0003 decided how a request proves *who* is asking. It left open what
that key may then do, and how keys come to exist. Until now every enabled
key may do everything, and the only way to create one is the bootstrap
environment variable, which `docs/configuration.md` calls a stopgap.

Stage 3 of the ladder (ADR-0004) is where the answer lives, and today it
holds one rule: some routes need a caller, some do not. This record fills
in the rest.

Forces:

- **Who deploys this.** One operator running a self-hosted store for a
  handful of applications, or one application with a few environments.
  Not a multi-tenant cloud with thousands of principals. The model has to
  be explainable on one screen and implementable in every SDK in an
  afternoon, since key management is part of every SDK's surface.
- **Least privilege where it matters.** A key that lives in a web app's
  environment should not be able to delete every bucket. A presigned URL
  handed to a browser is a credential; whatever it authorizes must be as
  narrow as possible.
- **Lifecycle without restarts.** Create a key for a new app, disable a
  leaked one, rotate a secret on schedule, delete what is no longer used,
  all over the API and effective immediately, including for presigned URLs
  already issued (ADR-0003: the key is looked up at use time).
- **The bootstrap variable stays.** It is the recovery path when the last
  administrative key is lost, and it must keep working after this record.
- **Disclosure.** ADR-0004 stage 3 says a forbidden request must not
  reveal whether the resource exists.
- **Speed.** Stage 3 runs on every request. It must be a lookup in the key
  record already fetched at stage 2, no extra store call.

## Options considered

### Option A: Every key does everything (status quo)

**Pros:** nothing to build; nothing for SDKs to model.

**Cons:** one leaked key is total compromise; a browser-facing app needs
the same key as the admin; no way to give one app one bucket. Fails the
least-privilege force outright. Kept only as the state before this record.

### Option B: Two kinds of key, scoped by bucket

An **admin** key may do everything, including manage keys and buckets. A
**scoped** key holds a map from bucket name to an access level, `read` or
`write`, where `write` includes `read`. The wildcard bucket `*` grants the
level on every bucket, present and future. Scoped keys cannot manage keys
or create and delete buckets.

**Pros:** explainable in three sentences; one JSON field on the key
record; stage 3 is a map lookup; covers the deployments in the context
section: an admin key for the operator, a `write` key per app, a `read`
key for a consumer, a browser that only ever gets presigned URLs.

**Cons:** no per-key prefix restriction within a bucket; no separate
delete permission; no conditions such as IP or time. Any of these can be
added later as a new field without breaking the two-level model, and none
has a requester today.

### Option C: A policy language (actions, resources, conditions)

IAM's shape: statements of effect, action list, resource patterns,
conditions.

**Pros:** expresses anything.

**Cons:** every SDK needs a policy model and every operator needs to learn
one; the evaluation engine is a subsystem with its own bugs and its own
vectors; the deployments this store targets would use one percent of it.
Rejected as the wrong size.

### Option D: One key per bucket

A key belongs to exactly one bucket.

**Pros:** simplest possible scope.

**Cons:** an app that uses two buckets needs two keys and two signers; an
app that creates buckets cannot exist. Rejected as too rigid, and Option B
contains it as the one-entry case.

## Decision

**Option B.**

### Key record

```
id        tk_<16 hex>       public, safe to log
secret    <43 base64url>    returned once, at create and at rotate
name      free text         a label for humans, e.g. "web-prod"
admin     bool
scopes    { "<bucket>|*": "read" | "write" }   ignored when admin is true
disabled  bool
created_at
```

Ids and secrets are generated by the server from the operating system's
random source; a client never chooses either. The bootstrap key is an
admin key with the name `bootstrap`.

### What each route requires

| Route | Requires |
|-------|----------|
| health, version | nothing |
| object GET, HEAD, list on a public bucket | nothing |
| object GET, HEAD, list | `read` on the bucket |
| object PUT, DELETE; upload initiate, part, query, complete, abort | `write` on the session's bucket |
| bucket GET | `read` on the bucket |
| bucket list | any key; the list is filtered to buckets the key can read; admin sees all |
| bucket create, delete | admin |
| every `/-/keys` route | admin |

"On the bucket" means the key is admin, or its scopes hold that bucket or
`*` at the level or higher. Upload routes are checked against the
session's bucket after the session is loaded, since the id alone does not
name a bucket; a key that may not write the bucket cannot touch the
session, whoever created it.

### Refusal

A key that lacks the required level answers `forbidden` at stage 3,
**before** the bucket or object is looked up, so the response is the same
whether or not the resource exists. The one exception is the upload
routes, where the session must be loaded to learn the bucket; an unknown
session is `upload_not_found` for everyone, and a known one is `forbidden`
for a key without `write` on its bucket. Session ids are random and
unguessable, so this leaks nothing.

### Presigned URLs

A presigned URL carries its signing key's scope, no more and no less. It is
already as narrow as a request can be: the signature binds one method, one
path and the listed headers. A URL signed by a `read` key for a `GET`
cannot be turned into a `PUT`; a URL signed by an admin key for a `GET`
authorizes exactly that `GET`. Disabling or rotating the key invalidates
every URL it signed, immediately (ADR-0003).

### Key management routes

| Route | Body | Response |
|-------|------|----------|
| `POST /-/keys` | `{"name", "admin", "scopes"}` | `201` with the record **including the secret**, the only time it is shown |
| `GET /-/keys` | | `200 {"keys": [record without secret, ...]}` by id |
| `GET /-/keys/{id}` | | `200` record without secret |
| `PATCH /-/keys/{id}` | any of `{"name", "admin", "scopes", "disabled"}` | `200` updated record |
| `POST /-/keys/{id}/rotate` | | `200` record **with the new secret**; the old one stops verifying at once |
| `DELETE /-/keys/{id}` | | `204` |

An unknown id is `key_not_found`. A scoped key that reaches these routes is
`forbidden`. `admin: true` with `scopes` set is `invalid_parameter`; the
two are exclusive so a record cannot be read two ways.

An admin may disable, rotate or delete its own key, and may disable the
last admin. The server does not prevent lockout; the bootstrap variable
is the documented recovery, and preventing it would make the rules
depend on a count that races.

### Effect on the authentication stage

Stage 2 already fetches the key record for the signature check. Stage 3
reads `admin` and `scopes` from that record; no second store call. A
future in-memory key cache (from the GET profile in
`docs/benchmarks/http-load.md`) must be invalidated by every key route
above, since the same process serves both, and bounded by a short TTL
regardless.

## Consequences

Easier:

- One JSON field and one boolean express every permission the target
  deployments need. Every SDK models a key as a record with a map.
- Stage 3 is pure: a function of the key record, the route and the bucket
  name, with vectors in `spec/vectors/authorization.json` so every SDK
  can predict what the server will say.
- Leaked keys are contained by scope and killed by one request.

Harder:

- `KeyStore` grows from one method to five, and the SQLite adapter gets
  migration 4 with three new columns on `api_keys`.
- Bucket list must filter by scope, which is the one place authorization
  touches a query rather than a single decision.
- Upload routes authorize after the session load, an exception to
  "stage 3 before stage 6" that the wire contract must state plainly.

To revisit:

- Prefix restrictions within a bucket, a `delete` level distinct from
  `write`, or expiring keys: each is a new field on the record and a new
  row in the vectors, without changing the model.
- Whether presigned URLs should be able to carry a scope narrower than the
  key. Not needed while the signature already binds method and path.
