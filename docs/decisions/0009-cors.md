# ADR-0009: CORS

**Status:** Accepted
**Date:** 2026-09-14
**Deciders:** maintainer

## Context

Browser pages are a first-class client. The predecessor's main use was a
web app uploading straight to the store with presigned URLs, so the page's
bytes never crossed the app server, and public buckets serving a site's
assets to any page that embeds them. Both need the store to answer CORS:
a preflight `OPTIONS` before a `PUT` with custom headers, and
`Access-Control-Allow-Origin` on the real responses, or the browser
refuses to let the page see them.

The wire contract's section 10 holds three rules carried from platform
facts and a placeholder that says the configuration is per bucket, with
the shape to be decided. This record decides the shape, and it changes the
placeholder.

Forces:

- **Nothing here is ambient.** The store has no cookies, no sessions and
  no HTTP basic auth. Every request carries an explicit signature or a
  presigned query, and a browser only sends those when the page's code
  puts them there. CORS exists to stop a hostile page from riding on
  credentials the browser attaches by itself. There are none to ride on.
  An origin allowlist therefore restricts nothing an attacker could not do
  from `curl`; it is hygiene and cache correctness, not a security
  boundary. This is the fact that sizes the design.
- **Caches.** A CDN in front will serve one origin's
  `Access-Control-Allow-Origin` to every other origin unless the response
  says `Vary: Origin`. Any response that echoes an origin must vary by it.
- **Wildcards.** `https://*.example.com` must match exactly one DNS label
  and never `https://evil-example.com`. A too-loose pattern is a silent
  grant; a too-tight one is a readable browser error; no same-origin test
  distinguishes them. The pattern rule needs vectors.
- **Origins are normalised by the browser.** The default port is omitted,
  the scheme and host are lowercase, and an `https` page may call
  `http://localhost`. The matcher must compare what browsers send, not
  what operators type.
- **Preflights are anonymous.** A browser never attaches `Authorization`
  or the signed date header to an `OPTIONS` preflight, so preflight must
  be answered before stage 2 of the ladder (ADR-0004), or every one of
  them is `unauthenticated`.
- **The control plane is in the same origin as the data.** A browser admin
  page that manages keys talks to `/-/keys`, which has no bucket. Whatever
  the design, it must cover routes that are not under a bucket.
- **Fast and simple.** One operator, one binary, environment
  configuration (`docs/configuration.md`). A CORS decision on the hot path
  is a string comparison, not a lookup.

## Options considered

### Option A: No CORS in the server; leave it to a reverse proxy

**Pros:** nothing to build; proxies have CORS modules.

**Cons:** contradicts the single-binary goal; every deployment repeats the
same configuration in a different dialect; proxies routinely get `Vary`
wrong and the CDN trap fires; the conformance suite cannot test what the
server does not do. Rejected.

### Option B: One server-wide allowlist from configuration

`TUNNA_CORS_ORIGINS` holds a comma-separated list of origins, each exact or
with a single-label wildcard, or `*` for any origin. Empty means CORS is
off and no CORS header is ever written. The same list answers every route,
control plane included.

**Pros:** one string comparison per request; no store lookup on preflight;
covers `/-/` routes; configuration is logged at startup like everything
else; the matcher is a pure function with vectors.

**Cons:** every bucket shares one list. A deployment hosting two apps on
two origins allows both origins on both buckets. Given the first force,
that costs nothing in security: a page from origin A can already reach
bucket B only with a key or URL scoped to B, and CORS never granted or
withheld that. It costs only tidiness.

### Option C: Per-bucket rules stored on the bucket record

S3's model: each bucket carries a list of `{origins, methods, headers,
max_age}` rules; preflight and responses on `/{bucket}/...` consult the
bucket.

**Pros:** matches S3, so familiar; per-tenant tidiness.

**Cons:** every preflight becomes a bucket lookup, or a cache with an
invalidation rule; `/-/` routes still need a second, global mechanism, so
this is two designs; the bucket record grows a nested structure that every
SDK must model and validate; the bucket routes gain a settings body with
its own faults. All of that buys tidiness on a boundary that, per the
first force, is not a security boundary here. S3 needs it because S3 has
ambient credentials in some configurations and multi-tenant accounts. This
store has neither.

### Option D: Option B now, Option C as a later narrowing

The global list is the policy; a bucket may later carry an optional list
that narrows it for that bucket. Nothing in B has to change for C to be
added, and C is not built until a deployment asks for it.

**Pros:** B's cost today; C's tidiness available without a wire break.

**Cons:** none beyond B's, provided the wire contract says the bucket
record's CORS field is reserved and absent.

## Trade-off analysis

**The absence of ambient credentials decides it.** The whole reason S3
puts CORS on the bucket is that a bucket is the tenant boundary and CORS
is part of the tenant's security posture. Here CORS guards nothing:
authorization is the signature and the scope (ADR-0003, ADR-0008), both
explicit, both already checked. What is left for CORS to do is to let the
right pages through and to keep caches honest. A global list does both,
and a per-bucket list does both at ten times the surface.

**Preflight is stage 0.** It runs before routing and before
authentication, because browsers send it bare. It is answered from
configuration alone, never from the store, so it cannot be used to probe
for bucket existence and it costs nothing under load. An `OPTIONS` that is
not a preflight, with no `Origin` or no `Access-Control-Request-Method`,
falls through to the router, which has no `OPTIONS` route, and gets what
any other wrong method gets: `method_not_allowed` on a known path,
`unknown_route` on an unknown one.

**Echo the requested headers; expose everything.** The request side lists
`Authorization` and the custom headers, which the `*` form of
`Access-Control-Allow-Headers` is defined not to cover, so preflight
echoes `Access-Control-Request-Headers` back. The response side is the
opposite: because the store never uses credentialed mode,
`Access-Control-Expose-Headers: *` is valid and exposes `ETag`,
`X-Tunna-Checksum`, `Content-Range` and every `X-Tunna-Meta-*` header
without the server maintaining a list that drifts from the wire contract.

**Match what browsers send.** An origin is compared as `scheme://host` or
`scheme://host:port`, host case-insensitively, after the operator's
configured value is normalised the same way a browser would: lowercase,
default port dropped. A pattern is `scheme://*.domain` and its `*` stands
for exactly one label, so `https://*.example.com` matches
`https://app.example.com`, not `https://example.com`, not
`https://a.b.example.com`, not `https://evil-example.com`. `*` alone
matches any origin and is answered with the literal `*`, which needs no
`Vary` because it is the same for everyone. Every other match echoes the
origin and adds `Vary: Origin`.

**A non-matching origin gets a normal response with no CORS headers.**
Not a 403: the request may be perfectly valid from a non-browser, and the
browser will refuse on its own. Refusing at the server would turn a
browser convenience into a wire error that non-browsers would then have to
understand.

## Decision

**Option D**, which is Option B today.

### Configuration

| Variable | Default | Meaning |
|----------|---------|---------|
| `TUNNA_CORS_ORIGINS` | empty | Comma-separated origins: exact (`https://app.example.com`), single-label wildcard (`https://*.example.com`), or `*`. Empty means no CORS headers are ever written. |

Values are trimmed, lowercased, and stripped of a default port (`:80` for
`http`, `:443` for `https`). A value that is not `*`, not `scheme://host`
and not `scheme://*.host` is a startup error naming the variable. Logged at
startup as the effective list.

### Preflight

A request is a preflight when the method is `OPTIONS` and both `Origin`
and `Access-Control-Request-Method` are present. It is answered before
stage 1 of the ladder, from configuration only:

- Origin matches: `204` with `Access-Control-Allow-Origin` (the origin, or
  `*`), `Access-Control-Allow-Methods: GET, HEAD, PUT, POST, PATCH,
  DELETE`, `Access-Control-Allow-Headers` echoing
  `Access-Control-Request-Headers` when present,
  `Access-Control-Max-Age: 86400`, and `Vary: Origin,
  Access-Control-Request-Method, Access-Control-Request-Headers`.
- Origin does not match, or CORS is off: `204` with no CORS headers.

The allowed method list is the union of every route's methods and does
not depend on the path; the router will still say `unknown_route` to the
real request if the method does not exist there. That keeps preflight free
of routing.

### Responses

Every response to a request carrying `Origin`, on every route, when the
origin matches: `Access-Control-Allow-Origin` (the origin, or `*`),
`Access-Control-Expose-Headers: *`, and `Vary: Origin` unless the value is
`*`. This includes error responses, so a page can read the error body.
Requests without `Origin`, non-matching origins, and CORS off: no CORS
headers.

### Matching

`spec/vectors/cors.json` is the definition. In prose: the request's
`Origin` value is compared byte for byte against each normalised entry;
for a wildcard entry, the origin must have the entry's scheme, end with
`.` plus the entry's domain, and have exactly one label before that
suffix, with no port unless the entry has one. `null` as an origin never
matches anything but `*`.

### Reserved

The bucket record has no CORS field. If Option C is ever built, it is a
`cors` field on the bucket that narrows the global list, and its absence
means "the global list", so nothing written against this record changes.

## Consequences

Easier:

- One environment variable, one pure matcher with vectors, one wrapper
  around the whole router. No store access, no new table, no new routes,
  no SDK model.
- Preflight cannot leak bucket existence and costs a string comparison.
- Every response, including errors, is readable by an allowed page.

Harder:

- One list for every bucket. Acceptable per the analysis; the reserved
  field is the escape hatch.
- The wrapper sits outside the ladder, so ADR-0004's "syntax first" now
  has one thing in front of it. The wire contract states it as stage 0.

To revisit:

- Per-bucket narrowing (Option C) when a deployment hosts apps that must
  not see each other's error bodies. Not before then.
- Whether the response header on a `*` match should echo the origin
  instead, so a future credentialed mode has nothing to change. Not while
  there is no such mode.

## Follow-ups this decision creates

- `docs/configuration.md`: the new variable.
- The wire contract's section 10 is rewritten from its placeholder, and
  the "bucket settings shape" open item shrinks to the public flag, which
  already exists.
